# TimeTree 일정 확인 스킬 + 일반 질의응답 — 설계도 (v0.1)

> 전제: [03-orchestrator.md](./03-orchestrator.md)의 Tool Registry에 스킬 하나를 추가하는
> 문서. 두뇌/실행 위치(PC)는 안 바뀜. **아직 코드 없음 — 설계만.**

결정된 전제 (이번 라운드):
- **일반 질의응답**: 일정/작업과 무관한 질문도 받아줄 것
- **TimeTree 접근 방식**: Chrome으로 timetreeapp.com 접속, Facebook 계정으로 로그인한
  세션을 재사용해서 읽기
- **트리거**: PC 켤 때마다(부팅/트레이앱 시작 시) 자동으로 신속하게 조회

추가 결정 (이번 라운드 2):
- **일정 구분**: TimeTree 캘린더에서 **초록색 바탕 + 흰 글씨**인 일정만 "내 일정". 나머지
  색상은 전부 "여자친구 일정"으로 따로 저장
- **PC 켜짐/꺼짐에 따른 응답 전략**: "오늘 일정 뭐 있어?" 질문이 오면 — PC가 켜져 있으면
  그 자리에서 다시 조회(갱신)해서 답변, PC가 꺼져 있으면 마지막으로 저장해둔 캐시로 답변

---

## 1. TimeTree API 조사 결과 — 공식 API는 못 씀

TimeTree의 공식 Connect API는 **2023년 12월 폐지**됐음. 지금 남은 건 리버스 엔지니어링된
비공식 엔드포인트(TimeTree-MCP 등 커뮤니티 프로젝트)뿐이고, 이건:
- ToS 위반 위험 (DESIGN.md 7번의 "ToS/탐지 위험"과 동일한 종류의 문제)
- TimeTree가 내부 구조를 바꾸면 예고 없이 깨짐

→ **Tier 1(공식 API) 불가, Tier 2(화면 읽기)로 간다.** 비공식 API도 안 쓴다 (안정성·ToS
리스크가 화면 읽기보다 딱히 안 나음).

## 2. 접근 방식 — Chrome 세션 재사용 + 스크린샷을 Claude에게

### 2.1 로그인은 절대 자동화하지 않음

Facebook 계정 로그인(아이디/비밀번호 입력)을 자동화하는 건 **하지 않는다.** 이건
Anthropic 에이전트 정책상 내가 직접 할 수도 없는 일이고, 설계상으로도 바람직하지 않음
(비밀번호를 코드/로그 어디에도 안 남기는 게 DESIGN.md 4.4의 원칙).

대신:
1. **전용 Chrome 프로필**을 하나 만든다 (`--user-data-dir=...timetree-profile` 같은 별도
   프로필 — 사용자의 평소 브라우징 프로필과 분리).
2. 사용자가 **최초 1회, 직접** 그 프로필에서 timetreeapp.com에 접속해 Facebook으로
   로그인한다. 로그인 세션(쿠키)이 그 프로필에 남음.
3. 이후 자동화는 그 프로필로 Chrome을 띄워서 **이미 로그인된 상태의 캘린더 페이지**를
   열기만 한다 — 인증 과정 자체를 건드리지 않음.
4. 세션이 만료돼서 로그인 화면이 나오면 → 아래 2.2에서 Claude가 스크린샷을 보고 "로그인이
   풀린 것 같다"고 그냥 알려줌. 별도 감지 로직 안 만듦 (단순함 우선).

### 2.2 읽기는 파싱 대신 스크린샷 + Claude Vision

캘린더 페이지의 DOM/UIA 구조를 파싱해서 일정을 뽑는 건 TimeTree 웹 UI가 바뀌면 바로
깨지는 약한 방법. 대신:

- 03문서에서 이미 설계한 `screenshot_window` 도구(`WindowPrintCapture` 그대로 재사용)로
  캘린더 화면을 캡쳐
- 그 이미지를 그대로 Claude에게 건넴 — Claude가 멀티모달이라 화면을 보고 일정을 직접
  읽고 정리함

→ **새로 쓸 파싱 코드가 거의 없음.** 기존 스크린샷 도구 재사용 + Claude의 비전 능력에
맡기는 쪽이 DOM 구조에 의존하는 것보다 훨씬 안 깨짐.

### 2.3 색깔로 "내 일정" vs "여자친구 일정" 구분 — 구조화된 출력 필요

단순 요약 문장만으로는 나중에 캐시(2.4)로 저장해서 PC 꺼져있을 때도 쓸 수 없음. 그래서
스크린샷을 건넬 때 프롬프트에 분류 규칙을 명시하고, Claude의 응답을 **구조화된 JSON**으로
받는다:

> "캘린더에서 **초록색 바탕에 흰 글씨**로 된 일정만 '나'의 일정이다. 그 외 색상은 전부
> '여자친구'의 일정이다. 보이는 일정을 날짜/시간/제목과 함께 두 목록으로 나눠서
> `{ "me": [...], "partner": [...] }` 형태로 반환해라."

→ 이 구조화된 결과가 사용자에게 보여줄 답변의 재료도 되고, 2.4의 캐시에 그대로 저장되는
데이터이기도 함.

### 2.4 영속 캐시 — PC가 꺼져 있을 때도 답하기 위한 저장소

04문서에서 이미 폰↔PC 연동에 Firestore를 쓰기로 했으므로, 같은 Firestore에 캐시를 둔다
(새 저장소를 따로 안 만듦):

```
schedule/me       { events: [{date, time, title}, ...], lastUpdated: <timestamp> }
schedule/partner  { events: [{date, time, title}, ...], lastUpdated: <timestamp> }
```

- `check_timetree_schedule`이 실행될 때마다(부팅 시 자동이든, 질문에 의한 수동이든) 2.3의
  구조화된 결과로 이 두 문서를 덮어씀
- 이게 "저장되어있는 일정 정보"의 실체 — PC가 꺼져 있어도 폰은 이 문서를 그대로 읽을 수 있음

## 3. 새 스킬: `check_timetree_schedule`

| 항목 | 내용 |
|---|---|
| 계층 | Tier 2, 읽기 전용 (클릭/입력 없음 — 페이지 이동 + 캡쳐만) |
| 매핑 | 전용 Chrome 프로필 실행 → timetreeapp.com 캘린더 페이지로 이동 → 로드 대기 → `WindowPrintCapture`로 캡쳐 → 이미지를 tool_result로 반환 |
| 입력 | 없음 (또는 선택적으로 "오늘"/"이번 주" 범위 힌트) |
| 출력 | 캘린더 화면 이미지 → Claude가 2.3 규칙대로 `{me, partner}` 구조화 데이터로 분류 → 2.4 캐시에 저장 |

## 4. 트리거 — 자동(부팅 시) + 수동(질문) 둘 다

| 트리거 | 동작 |
|---|---|
| **자동**: PC 부팅/트레이앱 시작 시 | 트레이앱이 뜨자마자 **백그라운드**로 `check_timetree_schedule` 실행 (트레이 아이콘 자체는 안 기다리고 바로 뜸) → 끝나면 윈도우 토스트로 오늘 일정 요약 표시 + 2.4 캐시 갱신. DESIGN.md 4.3 스케줄러의 트리거 종류에 "PC 부팅/로그인 시"를 cron 트리거와 나란히 추가 |
| **수동**: 사용자가 "오늘 일정 뭐있어?" 같은 자연어로 물어볼 때 | 아래 4.1/4.2의 PC 온/오프라인 분기를 먼저 거침 |

"신속하게"의 의미: 트레이앱 기동을 이 조회 때문에 블로킹하지 않음 (비동기로 바로 시작),
Chrome 페이지 로드 1회 + 캡쳐 1회라 보통 수 초 내 완료.

### 4.1 PC 켜짐/꺼짐 판단 — Firestore presence

PC 상주 앱이 실행 중일 때 주기적으로(예: 1분마다) `presence/pc { lastSeen: <timestamp> }`를
갱신. 폰은 이 값이 최근(예: 2분 이내)이면 "PC 켜짐", 오래됐으면 "PC 꺼짐"으로 판단. 정확한
전원 상태가 아니라 "트레이앱이 최근에 살아있었는가"를 보는 것 — 그걸로 충분함 (간단함 우선,
04문서가 이미 Firestore를 쓰기로 했으니 별도 체계 안 만듦).

### 4.2 "오늘 일정 뭐 있어?" 질문 처리 분기

- **PC 켜짐으로 판단됨**: 평소처럼 04문서의 흐름대로 Firestore에 요청 적재 → PC의
  Orchestrator가 `check_timetree_schedule`을 다시 실행(갱신) → 방금 갱신된 최신 데이터로
  답변 작성 → 폰에 결과 전달
- **PC 꺼짐으로 판단됨**: PC에 처리를 맡기지 않음(실행할 Orchestrator가 없으니까) — 대신
  폰이 2.4의 캐시(`schedule/me`, `schedule/partner`)를 **직접 Firestore에서 읽어서**, 캐시의
  `lastUpdated` 시각과 함께 "마지막으로 확인한 기준(n시간 전) 일정: ..."처럼 바로 보여줌.
  이 경로는 Claude를 다시 부르지 않고 캐시된 구조화 데이터를 그대로 포맷만 해서 보여주는
  **가장 단순한 방법으로 가정**했음 — 더 자연스러운 문장으로 다듬고 싶으면 폰 쪽에도 Claude
  호출을 추가할 수 있지만, 그러면 04문서의 "폰은 씬 클라이언트" 원칙에 예외가 생기는 것이니
  필요해지면 그때 다시 결정.
  - 03문서가 채팅방 모델로 바뀌면서, 이 경우에도 사용자의 질문과 폰이 캐시로 만든 답변을
    **같은 `conversations/{uid}/messages` 컬렉션에 user/assistant 메시지로 그대로 기록**함
    (`source: "phone-cache"`처럼 구분). 그래야 PC가 나중에 켜져서 채팅창을 봐도 대화가 끊긴
    것처럼 안 보임.

## 5. 일반 질의응답 — 사실 이미 되는 것

Orchestrator가 도구를 하나도 안 부르고 그냥 텍스트로 답해도 되는 구조이므로(03문서 2번
흐름의 `end_turn` 경로), "오늘 날씨 어때", "이거 어떻게 생각해?" 같은 일정·작업과 무관한
질문도 추가 설계 없이 바로 처리됨. 03문서에 이 용도를 명시적으로 한 줄 추가만 하면 됨
(실제 구조 변경 없음).

## 6. 미결정 사항

- [ ] 조회 범위 기본값 — 오늘만 vs 이번 주 (스크린샷에 뭐가 보이느냐에 따라 달라짐, 캘린더
      뷰를 "주간"으로 맞춰둘지)
- [ ] 로그인 세션이 실제로 끊겼을 때 사용자에게 "다시 로그인해주세요" 안내를 토스트로 띄울지,
      그냥 다음 질문 답변에 섞어서 알릴지
- [ ] 전용 Chrome 프로필을 매번 새로 띄울지(느릴 수 있음), 백그라운드에 계속 띄워둘지(메모리
      상시 사용) — "신속하게"와 트레이드오프
- [ ] PC 꺼짐 상태일 때 폰의 답변을 캐시 그대로 포맷(가정) vs 폰에서도 Claude 호출해서 더
      자연스럽게 다듬을지 (4.2 참고 — 현재는 전자로 가정)
- [ ] "초록 바탕+흰 글씨=내 일정" 규칙이 틀리게 분류되는 경우(예: 겹치는 일정, 테마 변경)를
      어떻게 확인/보정할지

## 7. 로드맵

1. **Step 1**: 전용 Chrome 프로필 생성 + 수동 로그인 1회 (사람이 직접)
2. **Step 2**: `check_timetree_schedule` 스킬 구현 → 수동 호출(CLI)로 캘린더 캡쳐 + 2.3의
   `{me, partner}` 구조화 분류까지 한 번 검증 (색깔 분류가 실제로 맞게 나오는지 확인)
3. **Step 3**: 2.4 캐시를 Firestore에 쓰기 → 트레이앱 부팅 트리거에 연결 → 컴퓨터 켰을 때
   자동으로 토스트 + 캐시 갱신되는지 확인
4. **Step 4**: 03/04문서 Orchestrator에 "오늘 일정" 자연어 질문으로도 같은 스킬이 불리는지
   확인 (PC 켜진 상태 기준)
5. **Step 5**: 4.1의 presence 하트비트 추가 + PC 꺼진 상태를 의도적으로 만들어서 폰이 캐시로
   답하는 경로(4.2) 검증
