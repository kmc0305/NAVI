# TimeTree 일정 확인 스킬 + 일반 질의응답 — 설계도 (v0.1)

> 전제: [03-orchestrator.md](./03-orchestrator.md)의 Tool Registry에 스킬 하나를 추가하는
> 문서. 두뇌/실행 위치(PC)는 안 바뀜. **아직 코드 없음 — 설계만.**

결정된 전제 (이번 라운드):
- **일반 질의응답**: 일정/작업과 무관한 질문도 받아줄 것
- **TimeTree 접근 방식**: Chrome으로 timetreeapp.com 접속, Facebook 계정으로 로그인한
  세션을 재사용해서 읽기
- **트리거**: PC 켤 때마다(부팅/트레이앱 시작 시) 자동으로 신속하게 조회

## 1. TimeTree API 조사 결과 — 공식 API는 못 씀

TimeTree의 공식 Connect API는 **2023년 12월 폐지**됐음. 지금 남은 건 리버스 엔지니어링된
비공식 엔드포인트(TimeTree-MCP 등 커뮤니티 프로젝트)뿐이고, 이건:
- ToS 위반 위험 (DESIGN.md 7번의 "ToS/탐지 위험"과 동일한 종류의 문제)
- TimeTree가 내부 구조를 바꾸면 예고 없이 깨짐

→ **Tier 1(공식 API) 불가, Tier 2(화면 읽기)로 간다.** 비공식 API도 안 쓴다 (안정성·ToS
리스크가 화면 읽기보다 딱히 안 나음).

## 2. 접근 방식 — Chrome 세션 재사용 + 스크린샷을 Claude에게

### 2.1 로그인은 절대 자동화하지 않음

Facebook 계정 로그인(아이디/비밀번호 입력)을 자동화하는 건 **하지 않는다.** 이건
Anthropic 에이전트 정책상 내가 직접 할 수도 없는 일이고, 설계상으로도 바람직하지 않음
(비밀번호를 코드/로그 어디에도 안 남기는 게 DESIGN.md 4.4의 원칙).

대신:
1. **전용 Chrome 프로필**을 하나 만든다 (`--user-data-dir=...timetree-profile` 같은 별도
   프로필 — 사용자의 평소 브라우징 프로필과 분리).
2. 사용자가 **최초 1회, 직접** 그 프로필에서 timetreeapp.com에 접속해 Facebook으로
   로그인한다. 로그인 세션(쿠키)이 그 프로필에 남음.
3. 이후 자동화는 그 프로필로 Chrome을 띄워서 **이미 로그인된 상태의 캘린더 페이지**를
   열기만 한다 — 인증 과정 자체를 건드리지 않음.
4. 세션이 만료돼서 로그인 화면이 나오면 → 아래 2.2에서 Claude가 스크린샷을 보고 "로그인이
   풀린 것 같다"고 그냥 알려줌. 별도 감지 로직 안 만듦 (단순함 우선).

### 2.2 읽기는 파싱 대신 스크린샷 + Claude Vision

캘린더 페이지의 DOM/UIA 구조를 파싱해서 일정을 뽑는 건 TimeTree 웹 UI가 바뀌면 바로
깨지는 약한 방법. 대신:

- 03문서에서 이미 설계한 `screenshot_window` 도구(`WindowPrintCapture` 그대로 재사용)로
  캘린더 화면을 캡쳐
- 그 이미지를 그대로 Claude에게 건넴 — Claude가 멀티모달이라 화면을 보고 일정을 직접
  읽고 정리함

→ **새로 쓸 파싱 코드가 거의 없음.** 기존 스크린샷 도구 재사용 + Claude의 비전 능력에
맡기는 쪽이 DOM 구조에 의존하는 것보다 훨씬 안 깨짐.

## 3. 새 스킬: `check_timetree_schedule`

| 항목 | 내용 |
|---|---|
| 계층 | Tier 2, 읽기 전용 (클릭/입력 없음 — 페이지 이동 + 캡쳐만) |
| 매핑 | 전용 Chrome 프로필 실행 → timetreeapp.com 캘린더 페이지로 이동 → 로드 대기 → `WindowPrintCapture`로 캡쳐 → 이미지를 tool_result로 반환 |
| 입력 | 없음 (또는 선택적으로 "오늘"/"이번 주" 범위 힌트) |
| 출력 | 캘린더 화면 이미지 → Claude가 자연어로 요약해서 최종 답변 생성 |

## 4. 트리거 — 자동(부팅 시) + 수동(질문) 둘 다

| 트리거 | 동작 |
|---|---|
| **자동**: PC 부팅/트레이앱 시작 시 | 트레이앱이 뜨자마자 **백그라운드**로 `check_timetree_schedule` 실행 (트레이 아이콘 자체는 안 기다리고 바로 뜸) → 끝나면 윈도우 토스트로 오늘 일정 요약 표시. DESIGN.md 4.3 스케줄러의 트리거 종류에 "PC 부팅/로그인 시"를 cron 트리거와 나란히 추가 |
| **수동**: 사용자가 "오늘 일정 뭐있어?" 같은 자연어로 물어볼 때 | 03/04문서의 기존 Orchestrator 루프가 그대로 처리 — 로컬 단축키 팝업이든 폰 앱이든 입력 경로 상관없이 같은 스킬 호출 |

"신속하게"의 의미: 트레이앱 기동을 이 조회 때문에 블로킹하지 않음 (비동기로 바로 시작),
Chrome 페이지 로드 1회 + 캡쳐 1회라 보통 수 초 내 완료.

## 5. 일반 질의응답 — 사실 이미 되는 것

Orchestrator가 도구를 하나도 안 부르고 그냥 텍스트로 답해도 되는 구조이므로(03문서 2번
흐름의 `end_turn` 경로), "오늘 날씨 어때", "이거 어떻게 생각해?" 같은 일정·작업과 무관한
질문도 추가 설계 없이 바로 처리됨. 03문서에 이 용도를 명시적으로 한 줄 추가만 하면 됨
(실제 구조 변경 없음).

## 6. 미결정 사항

- [ ] 조회 범위 기본값 — 오늘만 vs 이번 주 (스크린샷에 뭐가 보이느냐에 따라 달라짐, 캘린더
      뷰를 "주간"으로 맞춰둘지)
- [ ] 로그인 세션이 실제로 끊겼을 때 사용자에게 "다시 로그인해주세요" 안내를 토스트로 띄울지,
      그냥 다음 질문 답변에 섞어서 알릴지
- [ ] 전용 Chrome 프로필을 매번 새로 띄울지(느릴 수 있음), 백그라운드에 계속 띄워둘지(메모리
      상시 사용) — "신속하게"와 트레이드오프

## 7. 로드맵

1. **Step 1**: 전용 Chrome 프로필 생성 + 수동 로그인 1회 (사람이 직접)
2. **Step 2**: `check_timetree_schedule` 스킬 구현 → 수동 호출(CLI)로 캘린더 캡쳐 + Claude
   응답까지 한 번 검증
3. **Step 3**: 트레이앱 부팅 트리거에 연결 → 컴퓨터 켰을 때 자동으로 토스트 뜨는지 확인
4. **Step 4**: 03문서 Orchestrator에 "오늘 일정" 자연어 질문으로도 같은 스킬이 불리는지 확인
