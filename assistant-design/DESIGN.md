# 로컬 OS 개인비서 프로그램 — 설계도 (v0.1)

> NAVI(Android) 프로젝트와는 무관한 별도 프로그램입니다. 작업 편의상 이 폴더에 임시로
> 정리했으며, 실제 구현 시 별도 리포지토리/폴더로 분리하는 걸 권장합니다.

결정된 전제:
- **범위**: 하이브리드 (반복 작업은 전용 API 연동 / 그 외는 범용 화면 제어)
- **제어 방식**: Windows UI Automation(UIA) API 중심
- **승인 정책**: 완전 자율 실행 (매 작업 확인 없음)
- **실행 형태**: 상주 트레이 앱

---

## 1. 목표

사용자가 평소 반복적으로 하는 PC 작업(블로그 포스팅, SNS 업로드, 메시지 전송, 일정성
작업 등)을 명령 한 번 또는 스케줄로 맡기면, 사람이 매번 개입하지 않고 Windows 위에서
직접 실행해주는 상주형 비서.

## 2. 범위 정의 — "하이브리드"가 의미하는 것

작업을 두 계층으로 나눔:

| 계층 | 대상 | 실행 방식 |
|---|---|---|
| **Tier 1 — 전용 연동** | 공식 API가 있는 서비스 (워드프레스, X, Threads/Instagram Graph API, 네이버 블로그, 카카오 비즈 메시지 등) | REST API 직접 호출. 빠르고 안정적, UI 변화에 영향 안 받음 |
| **Tier 2 — 범용 UI 제어** | API가 없거나 개인 계정 기반이라 API 사용이 불가능한 모든 것 (카카오톡 개인 메시지, 임의의 데스크톱 앱, 레거시 프로그램) | Windows UI Automation으로 창/컨트롤을 찾아 직접 조작 |

→ 새 작업이 생기면 "API가 있는가?"를 먼저 확인하고, 없을 때만 Tier 2로 떨어지는 구조.
이게 하이브리드의 핵심 분기점.

## 3. 전체 아키텍처

```

│                     Tray App (상주 프로세스)                   │

│  - 명령 입력창 (핫키로 호출되는 간단한 챗/커맨드 박스)                │

                │
┌───────────────▼─────────────────────────────────────────────┐
│                    Core Orchestrator (Brain)                  │

│  - LLM(Claude API)에게 "무엇을, 어떤 순서로" 실행할지 질의          │
│  - Tier1/Tier2 라우팅 결정                                     │

        │                                        │

│    Threads/카카오비즈  │              │  - UIA 트리 탐색             │
│    등 플러그인 어댑터    │              │  - Invoke/SetValue/SendKeys │

└──────────────────────┘              └──────────────────────────┘
        │                                        │
```

## 4. 컴포넌트 설계

### 4.1 Core Orchestrator (Brain)
- 입력: 사용자 명령(자연어) 또는 스케줄러가 발사한 트리거
- LLM에 "현재 가능한 액션 목록(API 커넥터 + UIA 액션 카탈로그)"을 도구(tool)로 제공하고,
  작업을 단계별 계획으로 분해하도록 함
- 계획을 Action Executor에 순차 전달, 실패 시 재시도/대체 경로 판단

### 4.2 Action Executor

**API 커넥터 모듈**
- 서비스별 어댑터를 플러그인 형태로 추가 (`IConnector` 인터페이스: `post()`, `send()`, `fetch()` 등)
- 예: `WordPressConnector`, `ThreadsConnector`, `KakaoBizConnector`
- 자격증명은 Credential Manager에서 런타임에만 로드, 코드/로그에 평문 저장 금지

**UI Automation 엔진**
- Windows UIA (.NET: `System.Windows.Automation` 또는 **FlaUI** 래퍼 권장)로 구현
- 핵심 동작:
  1. 대상 프로세스 실행/포커스
  2. AutomationId/Name/ControlType으로 요소 탐색
  3. `Invoke`, `SetValue`, `ExpandCollapse`, 텍스트 입력(`SendKeys` 또는 `ValuePattern`) 실행
- **Fallback**: UIA 트리가 부실한 앱(Electron 기반 앱 등)은 스크린샷 + OCR/템플릿 매칭으로
  좌표 클릭하는 보조 경로 필요 (카카오톡 PC 클라이언트가 여기 해당할 가능성 높음 — 아래 리스크 참고)

### 4.3 스케줄러
- cron 표현식 기반 트리거 (`"0 8 * * *"` → 매일 8시)
- 이벤트 기반 트리거 확장 가능 (예: 특정 창에 새 메시지 알림 뜨면 발동)

### 4.4 자격증명 관리
- Windows Credential Manager 또는 DPAPI로 암호화 저장
- 비서 프로세스만 복호화 가능, 디스크에 평문 키/토큰 존재 금지

### 4.5 메모리/컨텍스트 저장소
- SQLite: 실행 이력, 사용자 선호(예: "블로그는 항상 이 말투로"), 반복 작업 템플릿

### 4.6 안전장치 — 완전 자율이라도 권장하는 최소 장치
승인 절차 없이 자동 실행하기로 했지만, 다음은 "승인"이 아니라 "사고 대응" 장치라 별개로
꼭 넣는 걸 권장합니다:
- **킬 스위치**: 트레이 아이콘에서 즉시 "전체 중지" 1클릭
- **감사 로그**: 모든 실행(언제/무엇을/어떤 앱에)을 로컬에 기록 — 문제 생겼을 때 추적 유일한 수단
- **화이트리스트**: 비서가 건드릴 수 있는 앱/도메인 목록을 명시적으로 제한 (은행 앱, 결제 화면 등은
  기본 차단 권장)
- **드라이런 모드**: 새 작업 추가 시 "실제 실행 전 로그만 남기고 끝내는" 테스트 모드 토글

### 4.7 트레이 UI
- 상태 아이콘(대기/실행중/오류), 최근 실행 로그 팝업
- 핫키로 띄우는 명령 입력창 (자연어 명령 입력 → Orchestrator로 전달)

## 5. 기술 스택 제안

| 영역 | 추천 | 이유 |
|---|---|---|
| 구현 언어 | **C# (.NET 8)** | Windows UIA/트레이 앱 생태계가 가장 성숙. `FlaUI`로 UIA 래핑 용이 |
| UI Automation | FlaUI (UIA3 래퍼) | 원시 UIA API보다 탐색/대기 로직이 훨씬 간결 |
| 트레이 앱 | WinForms 또는 WPF (NotifyIcon) | 상주 트레이 앱 표준 패턴 |
| LLM | Claude API (Anthropic) | 계획 수립/명령 해석용 "브레인" |
| 로컬 저장 | SQLite | 설치 간단, 단일 사용자 환경에 적합 |
| 스케줄러 | Quartz.NET 또는 자체 cron 파서 | 가벼운 트리거면 자체 구현도 충분 |

> 참고: 현재 프로젝트가 Kotlin/Java(Android) 기반이라 언어를 통일하고 싶다면 JVM도 가능하지만,
> Windows UIA 바인딩(JNA 경유)이 빈약하고 유지보수 사례가 적어 비권장. 이 비서는 완전히
> 별도 스택(C#/.NET)으로 가는 걸 추천.

## 6. 대표 워크플로우 예시

**A. 매일 아침 8시 블로그 자동 포스팅**
스케줄러 트리거 → Orchestrator가 "오늘의 글감" 생성(LLM) → `WordPressConnector.post()` 호출
→ 성공/실패 Audit Log 기록 → 트레이 알림

**B. 카카오톡 개인 메시지 자동 응답** (Tier 2, UIA)
UIA가 카카오톡 창의 새 메시지 알림/뱃지를 감지 → 대화창 포커스 → 메시지 영역 텍스트 읽기
→ LLM이 답장 생성 → 입력창에 `SetValue` → 전송 버튼 `Invoke`

**C. 스레드/릴스 업로드**
영상/이미지 파일 준비 → 해당 SNS가 API 제공 시 Graph API 업로드, 아니면 UIA로 업로드
다이얼로그 조작 (파일 선택 → 캡션 입력 → 게시 버튼 클릭)

## 7. 리스크 & 고려사항 (코딩 전에 반드시 인지)

- **ToS/탐지 위험**: 카카오톡, 인스타그램 등 대부분의 메신저/SNS는 **비공식 자동화(봇)를
  약관으로 금지**하고 있고, 이상 패턴 감지 시 계정 정지 가능성이 있음. 공식 API가 있는 서비스는
  반드시 공식 API 우선 사용, 개인 계정 UIA 자동화는 본인 책임 범위임을 인지하고 진행.
- **UIA 커버리지 한계**: Electron/Chromium 기반 앱(카카오톡 PC 포함)은 네이티브 Win32 앱보다
  UIA 트리 노출이 불완전할 수 있어, 생각보다 Fallback(OCR/좌표클릭) 비중이 커질 수 있음
- **완전 자율의 부작용**: 승인 단계가 없으므로 LLM의 판단 오류가 바로 실행됨 → 화이트리스트와
  감사 로그가 사실상 유일한 안전망. 결제/삭제/금융 관련 앱은 화이트리스트에서 기본 제외 강력 권장
- **자격증명 보안**: API 키/토큰이 로컬에 상시 존재하므로, PC 자체가 침해되면 연결된 모든
  계정이 노출됨

## 8. 단계별 빌드 로드맵 (실제 코딩 시작할 때)

1. **Phase 1 (MVP)**: 트레이 앱 뼈대 + Tier 1 커넥터 1개(예: 블로그 포스팅)만 동작
2. **Phase 2**: UIA 엔진 기초 (창 탐색, 텍스트 입력, 클릭) — 범용 Windows 앱 1~2개로 검증
3. **Phase 3**: 스케줄러 + Orchestrator(LLM 연동)로 "명령 → 계획 → 실행" 파이프라인 완성
4. **Phase 4**: 카카오톡 등 까다로운 Tier 2 대상 추가 (OCR fallback 포함)
5. **Phase 5**: 감사 로그/킬스위치/화이트리스트 UI 정리, 안정화

## 9. 코딩 전에 정해야 할 미결정 사항

- [ ] 첫 번째로 자동화할 "킬러 유즈케이스" 1~2개 확정 (범위를 넓히기 전에 하나를 끝까지 완성)
- [ ] 카카오톡 자동화를 실제로 진행할지 (ToS 리스크 감수 여부) 최종 결정
- [ ] 화이트리스트에서 기본 차단할 앱/도메인 목록 초안
- [ ] LLM 호출 비용/빈도 설계 (매 트리거마다 API 호출할지, 규칙 기반으로 먼저 걸러낼지)
