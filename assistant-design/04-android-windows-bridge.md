# 안드로이드 ↔ 윈도우 연동 — 설계도 (v0.1)

> 전제: [03-orchestrator.md](./03-orchestrator.md)의 Orchestrator/Tool Registry는 그대로
> **PC에서만** 돈다. 이 문서는 "폰에서 입력 → PC가 실행"을 위한 **입력 채널 하나를 더
> 추가**하는 것일 뿐, 두뇌나 도구 실행 위치를 바꾸지 않는다. **아직 코드 없음 — 설계만.**

결정된 전제 (이번 라운드):
- **핵심 시나리오**: 폰 → PC 원격 지시 (PC 앞에 없을 때 폰으로 자연어 요청 → PC가 실행)
- **통신 범위**: 어디서든 (LAN 한정 아님 — 클라우드 릴레이 필요)

---

## 1. 바뀌는 것 / 안 바뀌는 것

| | 내용 |
|---|---|
| **안 바뀜** | Orchestrator(Claude 호출), Tool Registry, 안전장치(3.3/4) — 전부 PC에만 존재, 그대로 재사용 |
| **바뀜** | "입력 채널"이 2개로 늘어남: ① 기존 윈도우 전역 단축키 팝업 (로컬), ② 안드로이드 앱 (원격) |

→ 안드로이드 앱은 **씬 클라이언트**다. 자연어 텍스트를 PC로 전달하고 결과를 받아 보여주는
역할만 함. 폰에서 자체적으로 Claude를 호출하거나 도구를 실행하지 않음 (단순성 우선 — Tool
Registry를 두 플랫폼에 중복 구현/동기화할 필요가 없어짐).

## 2. 통신 아키텍처 — 클라우드 릴레이

같은 와이파이가 아니어도 되게 하려면 phone과 PC가 직접 연결(P2P)되기 어려움 (PC가 보통
공유기 뒤 NAT에 있어 외부에서 직접 못 들어옴) → 중간에 항상 켜져 있는 릴레이가 필요.

**추천: Firebase (Firestore + Cloud Messaging)** — 직접 서버를 만들고 호스팅/운영할 필요가
없는 서버리스 구성. 안드로이드 SDK가 성숙하고, PC(.NET)에서도 Firebase Admin SDK/REST로
붙을 수 있음.

```
[안드로이드 앱]                      [Firestore]                    [PC 상주 앱]
     │  자연어 입력                      │                                │
     ├─ write: requests/{uid}/{reqId} ──▶│                                │
     │   { text, status: "pending" }    │                                │
     │                                   │── 실시간 리스너로 즉시 감지 ──▶│
     │                                   │                           Orchestrator 루프 실행
     │                                   │                                │
     │                                   │◀── write: 같은 문서에 ─────────┤
     │                                   │    { status: "done", result } │
     │◀── 실시간 리스너로 결과 수신 ─────┤                                │
     │  (+ FCM 푸시로 백그라운드에서도 알림)                              │
```

- **PC가 꺼져 있을 때**: 요청은 `status: "pending"`으로 Firestore에 그냥 쌓여 있음. PC가
  켜지고 리스너가 다시 붙으면 쌓인 요청을 순서대로 처리. 안드로이드 앱은 "PC가 꺼져있어서
  대기 중"을 pending 상태로 그대로 보여주면 됨 — PC를 원격으로 깨우는 것(Wake-on-LAN 등)은
  이번 범위 밖, 필요해지면 나중에 별도 설계.
- **자체 서버를 안 만드는 이유**: 서버 호스팅/보안 패치/가동률을 직접 책임지는 것 자체가
  1인 개인용 프로젝트 규모에는 과한 유지보수 비용. Firebase는 이미 완성된 인증·실시간 동기화를
  거의 공짜로 제공 — 단, "메시지가 구글 클라우드를 거쳐간다"는 신뢰 모델 변화는 감수해야 함
  (아래 3번 참고).

## 3. 인증/보안 — "내 폰"과 "내 PC"만 짝지어지게

- Firebase Auth 계정 1개(본인 구글 계정 등)로 폰 앱과 PC 상주 앱 둘 다 로그인.
- Firestore 보안 규칙으로 `request.auth.uid == 문서의 ownerId`만 읽기/쓰기 허용 — 다른 사람
  계정은 구조적으로 내 요청을 못 보고 못 씀.
- PC 쪽 인증 토큰은 기존 설계(03문서 5번)와 동일하게 DPAPI로 로컬 암호화 저장.
- **왜 중요한가**: 이 연결 자체가 "PC에서 UIA 동작을 원격으로 트리거하는 입력 경로"이므로,
  계정이 뚫리면 곧바로 PC 제어권까지 넘어간다. Tool Registry의 좁은 화이트리스트(03문서
  3.3)는 그대로 적용되지만, 원격 입력 경로는 로컬 단축키보다 공격 표면이 넓다는 걸 인지하고
  진행.

## 4. 안드로이드 앱 — 최소 구성 (v1)

- 화면 1개: 입력창 + 전송 버튼 + 최근 요청/결과 리스트 (대화형 UI 아님, 그냥 로그처럼)
- FCM으로 결과 도착 시 푸시 알림 (앱이 백그라운드/종료 상태여도 받도록)
- 로그인 화면 (Firebase Auth, 최초 1회)

## 5. PC 상주 앱 쪽 추가 작업

- 기존 트레이 앱에 Firestore 리스너 추가 (03문서의 Orchestrator 루프 "입력 소스"가 이제
  팝업 텍스트뿐 아니라 Firestore 신규 문서 이벤트도 됨 — 둘 다 같은 Orchestrator.Run() 호출)
- 결과를 같은 문서에 write해서 되돌려줌

## 6. 미결정 사항

- [ ] 원격(폰) 입력에는 로컬 입력보다 더 엄격한 도구 제한을 걸지 (예: 특정 스킬은 PC 앞에
      있을 때만 허용) — 아직 안 정함
- [ ] Firebase 프로젝트를 개인 구글 계정으로 쓸지, 별도 계정으로 분리할지
- [ ] 안드로이드 앱 최소 지원 버전/기기 (이미 갖고 있는 폰 기준으로 맞추면 됨)
- [ ] 결과가 길 때(스크린샷 포함 등) Firestore 문서 크기 제한(1MB) 대응 — 필요시 Firebase
      Storage에 올리고 문서엔 링크만 저장

## 7. 로드맵

1. **Step A**: Firebase 프로젝트 생성 + PC 상주 앱에 Firestore 리스너만 추가 → 검증: Firebase
   콘솔에서 문서를 수동으로 하나 넣었을 때 PC가 반응하는지 (안드로이드 앱 없이 배관만 먼저 확인)
2. **Step B**: 최소 안드로이드 앱(입력창 + 전송) 제작 → 검증: 실제 폰에서 보낸 문장이 PC에서
   Orchestrator까지 도달하는지
3. **Step C**: 결과가 폰까지 돌아와 알림으로 뜨는지 확인
4. **Step D**: 보안 규칙 정식화 + PC 꺼짐 상태 표시 + 03문서의 안전장치(감사 로그 등)에
   "요청이 로컬/원격 중 어디서 왔는지" 필드 추가
