# PDF → PPTX 변환 — 최종 폴백 (슬라이드별 캡쳐/복사 재구성)

## 적용 조건

다음이 **모두** 실패했을 때만 쓰는 최종 수단:
1. CLI/배치 변환 불가
2. Polaris Office의 PDF→PPT 변환 기능을 UIA로 자동화 불가 (기능 없음/유료/UI 노출 안 됨)

## 설계 원칙 — 모든 단계는 "원자 단위 + 체크포인트"

실패 시 전체를 다시 하지 않기 위해, 전체 작업을 **작은 원자 단위(atomic unit)** 로
쪼개고 각 단위가 끝날 때마다 **진행 상태를 파일로 기록**한다. 재실행하면 오케스트레이터가
진행 상태 파일을 먼저 읽어서, 이미 끝난 단위는 건너뛰고 **실패한 지점부터만** 재개한다.

- 진행 상태 파일: `work/<작업ID>/progress.json`
  ```json
  { "last_completed_page": 4, "total_pages": 10 }
  ```
  (클립보드는 한 번에 하나만 들고 있을 수 있어서 "여러 페이지를 미리 캡쳐해두는 단계"
  자체가 없다 — 그래서 별도 캡쳐 목록은 필요 없고, 항상 빈틈없이 순서대로 진행되므로
  숫자 하나(`last_completed_page`)로 진행 상태를 표현할 수 있다)
- 원칙: 각 원자 단위는 **몇 번을 다시 실행해도 결과가 같아야 함(idempotent)**
- **클립보드 기반**: Chrome에서 복사 → Polaris에 붙여넣기. 한 페이지 처리(복사→붙여넣기→
  검증)가 끝나야 다음 페이지로 넘어간다 — 클립보드 특성상 "전부 미리 캡쳐"는 불가능하므로
  반드시 한 장씩 순차 처리
- **슬라이드 삽입 원칙**: 무조건 "새 슬라이드 추가"가 아니라 **빈 슬라이드가 있으면
  그걸 재사용하고, 없을 때만 새로 추가**한다
- **"슬라이드 하나"의 기준**: 브라우저(Chrome) 창에 표시된 **PDF 한 페이지**다. 복사/비교
  모두 그 페이지 전체가 한 화면에 들어오도록(필요 시 맞춤 줌) 한 상태를 기준으로 한다
- **검증 기준점은 그 순간의 브라우저 창 화면이다** — 저장된 파일이 아니라, **지금
  복사하려고 했던 인터넷 창(Chrome)의 그 슬라이드**와 붙여넣은 결과를 비교한다. 이 설계는
  처음부터 "파일로 전부 미리 저장"하는 단계가 없는 클립보드 기반 파이프라인이라, 비교
  기준도 그때그때의 브라우저 화면이어야 자연스럽다

## 단계

### 1단계 — PDF 총 페이지 수 파악
- Chrome PDF 뷰어의 페이지 표시(UIA) 읽기, 또는 마지막 페이지까지 스크롤해서 확인
- **성공 기준**: `progress.json`에 `total_pages` 기록됨
- **재개**: 실패해도 삭제할 게 없음 — 이 단계만 재시도

### 2단계 — Polaris Office 빈 프레젠테이션 준비
- Polaris Office 실행 → 새 프레젠테이션 생성 → 작업 경로에 저장
- 1단계와 독립적인 작업이라 순서를 바꿔서 먼저 해도 됨
- **성공 기준**: 빈 pptx 파일이 디스크에 존재 (기본 슬라이드 1장 포함 — 일부러 안 지움.
  3단계의 "빈 슬라이드 재사용" 규칙이 이걸 1페이지용으로 자동으로 씀)

### 3단계 — 페이지 1장 처리 원자 단위 정의 (1장으로 검증)

하나의 페이지를 처리하는 전체 동작을 다음 순서로 고정한다 (이 전체가 "원자 단위"):

1. Chrome에서 해당 페이지로 이동, 페이지 전체가 한 화면에 보이도록 맞춤줌 확인
2. 그 상태의 브라우저 창을 그대로 비교 기준으로 쓸 수 있게 둔다 (파일로 저장할 필요
   없음 — 바로 복사하고, 검증 때 다시 이 창을 보고 비교하면 됨)
3. 복사: Chrome에서 해당 페이지 콘텐츠를 클립보드로 복사 (Ctrl+C 또는 메뉴)
   - 주의: Chrome 내장 PDF 뷰어가 "페이지를 이미지로 복사"를 기본 지원 안 할 수 있음 →
     안 되면 화면 캡쳐한 이미지를 직접 클립보드에 설정하는 방식으로 대체 (이 경우 "복사한
     것"과 "비교 기준"이 같은 이미지라 아래 6번 검증이 더 단순해짐)
4. **빈 슬라이드 확보**: Polaris 덱의 마지막 슬라이드가 비어있는지(=이미지 없음, 기본
   placeholder 텍스트는 무시) 확인 → 비어있으면 재사용, 아니면 새 슬라이드 추가
5. 붙여넣기(Ctrl+V) → 비율 유지하며(왜곡 없이) 맞춤
6. **검증(실패 조건)**: 방금 붙여넣은 슬라이드를, **지금 복사하려고 했던 그 Chrome
   창의 슬라이드**(= 1~2번에서 보고 있던 그 페이지)와 비교
   - Chrome 창이 그사이 다른 페이지로 넘어갔거나 닫혔으면 → 그 자체로 실패 처리 (비교
     대상이 없어진 것이므로)
   - 비교는 완전 동일 픽셀 일치가 아니라 **허용 오차가 있는 비교**(perceptual hash,
     구조적 유사도 등)로 한다 — 복사/붙여넣기를 거치며 생기는 미세한 렌더링 차이까지
     "다름"으로 잡으면 영원히 통과 못 하는 무한 재시도가 생긴다
   - 다르면 **실패**: 붙여넣은 이미지만 삭제해 슬라이드를 다시 "빈 슬라이드" 상태로 되돌림
     (슬라이드 자체는 삭제하지 않음 → 다음 시도가 4번 규칙으로 바로 재사용)
   - 같으면 **성공**: `progress.json.last_completed_page`를 이 페이지 번호로 갱신
- **성공 기준**: 1장이 위 6단계를 모두 통과

### 4단계 — 전체 페이지에 3단계 반복 (★ 반드시 순차적으로만 진행)

- `1 → total_pages` 순서를 절대 건너뛰지 않는다: 매번 "다음에 처리할 번호 =
  `last_completed_page` + 1"만 시도. 클립보드가 한 번에 하나뿐이라 애초에 뒷번호를
  먼저 처리하는 것 자체가 불가능 — 동시에 여러 페이지를 복사해둘 수 없음
- **연속 실패 제한**: 같은 페이지에서 검증 실패가 **3회 연속** 발생하면 더 재시도하지
  않고 전체 작업을 중단 + 사용자에게 보고
- **재개 규칙**: 재실행 시 `last_completed_page` 다음 번호부터 3단계 루틴으로 이어서
  진행. 이때 "지금 실제 덱의 마지막 슬라이드가 비었는지"부터 확인하므로(3단계 4번),
  중간에 프로세스가 죽었다가 재시작해도 로그만 믿지 않고 **실제 상태를 먼저 확인한
  뒤** 이어가는 구조가 됨
- **방어적 트리밍**: 혹시라도 실제 슬라이드 수가 `last_completed_page + 1`보다 크면(=
  "빈 슬라이드로 되돌리기"가 중간에 실패해서 여분이 쌓인 경우) 초과분을 모두 삭제해
  트레일링 빈 슬롯을 정확히 1개로 맞추고 나서 진행
- **성공 기준**: `last_completed_page == total_pages`

### 5단계 — 저장 및 최종 완료 조건

pptx로 저장 후, 다음 **두 조건을 모두 만족**해야 완료로 인정한다:

1. **원본의 마지막 슬라이드**(= Chrome에서 `total_pages`번째 페이지)와 **복사본의
   마지막 슬라이드**가 같다 (3단계와 동일한 허용오차 비교)
2. 원본 슬라이드 개수(`total_pages`)와 복사본 슬라이드 개수가 같다

→ 매 페이지가 처리되는 시점에 이미 3단계에서 개별 검증을 통과했으므로, 이 최종
체크는 "혹시 마지막에 뭔가 틀어지지 않았는지"를 다시 한번 확인하는 이중 안전장치다.
불일치 시 **4단계를 그대로 재실행**해서 마지막 번호 다음부터 이어서 완성한다 — 끝에
끼워 넣는 동작은 하지 않는다.

## 요약 — 왜 이 순서가 "재작업 최소화"를 만족하는가

| 실패 지점 | 재개 방법 | 다시 안 해도 되는 것 |
|---|---|---|
| 특정 페이지 검증 실패(내용 다름) | 그 슬라이드만 다시 비우고 3단계 재시도 (같은 페이지) | 1~N-1페이지까지 이미 완성된 슬라이드 |
| 특정 페이지에서 복사/붙여넣기 자체가 실패 | 4단계만 재실행 (그 페이지부터 순서대로 이어서) | 1~N-1페이지까지 이미 완성된 슬라이드 |
| 최종 검증에서 개수/내용 불일치 | 4단계 재실행으로 이어서 완성 (끝에 끼워넣기 아님) | 이미 완성된 앞쪽 슬라이드 전부 |

1단계(페이지 수 파악)와 2단계(Polaris 준비)는 서로 독립이라, 둘 중 하나가 실패해도
다른 쪽에 영향 없음.

## 재검토 — 기존 발견 #3 ("재개 시 로그만 믿지 말고 실제 상태 대조") 다시 확인

**결론: 여전히 해소됨.** 구조가 "미리 다 캡쳐 후 나중에 다 삽입"에서 "한 페이지씩
복사-붙여넣기"로 바뀌었지만, 재개 메커니즘의 핵심은 동일하다 — 3단계 4번("빈 슬라이드
확보")이 매번 "지금 실제로 몇 장이 있고 마지막 게 비었는지"를 들여다보고 결정하므로,
재개 시 별도의 "사전 대조 단계" 없이 **로직 자체가 매 유닛마다 실제 상태를 확인**한다.

남는 틈(동일): "실패한 슬라이드를 다시 비우는" 동작 자체가 실패하면 트레일링 빈/오염
슬라이드가 쌓일 수 있음 → 4단계의 **방어적 트리밍**으로 막음. 이 둘을 합치면 #3은
여전히 완전히 닫힌다.

## 이번 수정으로 바뀌는 점 정리

1. **비교 기준이 저장 파일 → 그 순간의 Chrome 창**으로 바뀜. 미리 다 캡쳐해서 파일로
   쌓아두는 단계가 사라지고, "한 페이지 복사 → 붙여넣기 → 그 페이지를 다시 보고 비교"가
   하나의 원자 단위로 합쳐짐
2. 클립보드는 한 번에 하나만 들 수 있어서, **순차 처리가 선택이 아니라 구조적으로
   강제**됨 (여러 페이지를 동시에/미리 처리하는 경로 자체가 없음)
3. `progress.json`이 `captured_pages`/`built_slides` 두 목록에서 **`last_completed_page`
   숫자 하나**로 단순화됨 (항상 빈틈없이 순서대로 진행되므로 배열이 필요 없음)
4. **새로 생기는 위험**: Chrome 창이 복사 시점과 검증 시점 사이에 다른 페이지로 넘어가거나
   닫히면 비교 자체가 불가능 → 이 경우도 그냥 "검증 실패"로 처리(3단계 6번에 반영)하면
   되므로 별도 예외처리 없이 기존 재시도 로직으로 흡수됨
5. Chrome의 네이티브 복사가 기대한 이미지를 복사하지 않을 경우를 대비해, "캡쳐 후
   클립보드에 직접 설정"하는 대체 경로를 3단계 3번에 명시해둠
