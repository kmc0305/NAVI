# 자연어 개인 에이전트 (Core Orchestrator) — 설계도 (v0.1)

> 전제: [DESIGN.md](./DESIGN.md)에서 이미 정했던 "Core Orchestrator (Brain)" 레이어를
> 구체화하는 문서. [M1](../LocalAssistant) (크롬 PDF → Polaris PPTX 자동화, git tag `M1`)이
> 이 설계의 첫 번째 Tier 2 "스킬"이 된다. **아직 코드 없음 — 설계만.**

결정된 전제 (이번 라운드):
- **입력 방식**: 전역 단축키 팝업 (작은 입력창이 떠서 자연어 명령 입력)
- **판단 두뇌**: Claude API 연동 (Anthropic Messages API, tool use)

**수정 (이후 라운드)**: 단축키로 뜨는 게 "제출하면 사라지는 한 줄짜리 입력창"이 아니라
**Claude.ai처럼 대화가 쌓이는 채팅창**으로 바뀜. 작업 요청이든 그냥 잡담/질문이든 전부 같은
채팅방에서 자연스럽게 주고받음 — 2번/6번 참고.

---

## 1. 목표

사용자가 단축키를 눌러 "크롬에 열린 PDF를 PPT로 만들어줘" 같은 자연어 한 줄을 입력하면,
Claude가 (a) 이미 만들어둔 전용 스킬을 쓸지 (b) 범용 UI 조작 도구를 조합해서 즉석으로
처리할지 판단해서 실행하고, 결과를 알려주는 상주형 에이전트.

## 2. 전체 흐름

```
[전역 단축키] → [채팅창 열기/포커스] → 사용자가 메시지 입력(= 채팅방에 새 user 메시지)
                                   │
                                   ▼
                     ┌─────────────────────────┐
                     │   Orchestrator (루프)      │
                     │  이 채팅방의 지난 대화 기록 +  │
                     │  새 메시지를 Claude에 통째로  │
                     │  전달, tool_use 올 때까지/   │
                     │  끝날 때까지 반복             │
                     └──────────┬──────────────┘
                                │ tool_use
                                ▼
                     ┌─────────────────────────┐
                     │      Tool Registry        │
                     │  (아래 3번 참고)             │
                     └──────────┬──────────────┘
                                │ tool_result
                                ▼
                     (Claude에게 결과 돌려주고 다음 턴 요청 — 반복)
                                │
                                ▼ end_turn
                     [같은 채팅방에 assistant 메시지로 추가] + [감사 로그 기록]
```

핵심: **채팅방 하나 = 계속 이어지는 대화**. 사용자가 "크롬 PDF를 PPT로 만들어줘"라고 하든
"오늘 날씨 어때"라고 하든 같은 방에서 메시지 하나로 취급되고, Claude가 필요하면 도구를
여러 번 연달아 호출(예: 창 목록 보기 → 캡쳐 → 클릭)한 뒤 최종 답을 그 방에 남김. **요청 간
기억(대화 맥락)이 이제 핵심 요구사항**이다 — 매 메시지마다 이 방의 지난 대화 기록을 함께
Claude에 보내서, "그거 아까 한 거 다시 해줘" 같은 맥락 의존 발화도 자연스럽게 이해하게 함
(이전 버전 문서에서 "요청 간 기억 없음"으로 정했던 걸 뒤집음 — 아래 2.1 참고).

도구를 하나도 안 불러도 됨 — Claude가 그냥 텍스트로 답하면 끝나는 `end_turn` 경로도 당연히
있음. 작업 요청과 일반 질문을 UI나 흐름에서 구분하지 않음 — 둘 다 같은 채팅방의 메시지일
뿐이라 애초에 "작업 모드"와 "채팅 모드"를 나눌 필요가 없어짐 ([05번 문서](./05-timetree-schedule-skill.md) 5번 참고).

### 2.1 대화 기록 보관

- 채팅방의 메시지 히스토리는 로컬에 영속 저장(예: SQLite 또는 JSON 파일) — 앱을 껐다 켜도
  대화가 이어짐
- 매 요청마다 전체 히스토리를 다 보내지는 않음 — 토큰/비용 관리는 7번 참고
- 04문서(폰 연동)에서 이 채팅방이 폰과 PC 양쪽에서 공유되는 **하나의** 대화가 됨 — 자세한
  저장 위치는 04문서 2번 참고

### 2.2 작업 큐 — "직렬화"는 도구 실행에만 걸림, 대화는 안 막힘

작업(도구 호출)이 여러 개 겹치면 **도구 실행 자체만 큐에 쌓아서 하나씩** 처리한다. 반면
**Claude API 호출(= 대화 자체)은 직렬화하지 않는다** — 그래서 작업이 진행 중이어도 다른
질문을 바로 물어보고 답을 받을 수 있다.

- 메시지가 오면 일단 바로 Claude에 보냄 (이전 메시지의 작업이 진행 중이어도 기다리지 않음)
- Claude 응답이 **일반 텍스트**(`end_turn`, 도구 호출 없음)면 그 자리에서 바로 채팅방에
  표시 — 아무것도 기다릴 필요 없음. "작업 중에도 질문 가능"이 이 경로로 그냥 충족됨
- Claude 응답이 **도구 호출**(`tool_use`)이면, 실제 UIA 엔진(Chrome/Polaris 등)은 동시에
  여러 작업을 못 하므로 **Task Runner라는 단일 실행 슬롯(세마포어 1개)**을 먼저 잡아야 함.
  이미 다른 작업이 그 슬롯을 쓰고 있으면 큐에 들어가서 "대기 중 (앞 작업 완료 후 진행)"으로
  표시되고, 앞 작업이 끝나면 순서대로 실행됨
- 왜 이렇게 나누나: 직렬화가 필요한 진짜 이유는 "Claude에게 너무 많이 물어봐서"가 아니라
  "같은 Chrome/Polaris 창을 동시에 두 자동화가 건드리면 꼬인다"는 물리적 제약 때문. 그 제약이
  실제로 있는 지점(도구 실행)에만 직렬화를 걸고, 아무 제약이 없는 지점(그냥 대화)은 막지 않음

## 3. Tool Registry — Claude에게 뭘 쥐어줄 것인가

두 계층으로 나눔. **이 구분 자체가 안전장치**다 — "위험한 건 LLM이 판단해서 피하길
기대"하는 게 아니라, 애초에 그런 동작을 하는 도구 자체를 레지스트리에 안 넣는다.

### 3.1 전용 스킬 (고수준, 이미 검증된 파이프라인)

| 도구 이름 | 매핑 | 비고 |
|---|---|---|
| `convert_chrome_pdf_to_pptx` | `PolarisLauncher` + `PdfToPptxJob.Run` (M1) | 입력: 크롬 창 제목 힌트(선택). 이미 끝까지 검증됨 |
| `check_timetree_schedule` | 전용 Chrome 프로필 + `screenshot_window` | [05번 문서](./05-timetree-schedule-skill.md) 참고 — 읽기 전용, Claude Vision으로 해석 |

새 반복 작업이 생기면 이 레이어에 하나씩 추가 (예: 나중에 "블로그 포스팅" Tier 1 커넥터가
생기면 여기 합류).

### 3.2 범용 원시 도구 (저수준, Tier 2 UIA 엔진 재사용)

스킬이 없는 낯선 요청도 처리할 수 있게 하는 즉석 조합용 도구:

| 도구 이름 | 매핑 | 설명 |
|---|---|---|
| `list_windows` | `WindowLister` | 현재 떠 있는 창 이름 목록 (읽기 전용) |
| `dump_window` | `UiaTreeDumper` | 특정 창의 UI 구조(버튼/텍스트 등) 텍스트로 보기 (읽기 전용) |
| `screenshot_window` | `WindowPrintCapture` | 창을 이미지로 캡쳐해서 Claude에게 그대로 보여줌 (포커스 무관, 읽기 전용) — 대상이 크롬이면 [06번 문서](./06-chrome-extension.md)의 텍스트 추출을 먼저 시도하고 이건 fallback |
| `click_element` | `ButtonClicker` | 이름으로 버튼/링크 Invoke (실제 마우스 클릭 아님 — 포커스 무관) |
| `set_text_value` | (신규, ValuePattern 래퍼) | 입력창에 `SetValue`로 텍스트 주입 (키 입력 시뮬레이션 아님) |

네 개는 이미 M1에서 만든 모듈 그대로 재사용, `set_text_value`만 `ChromePdfViewer.GoToPage`에서
썼던 `ValuePattern.SetValue` 패턴을 일반화해서 신규 작성.

→ `click_element`/`set_text_value`가 "실제 마우스/키보드 시뮬레이션이 아니라 UIA 네이티브
호출"이라는 제약은 그대로 유지 — 이게 게임 중에도 안전하게 동작하게 만든 핵심 원칙이었으니
범용 도구에도 똑같이 적용.

### 3.3 절대 안 넣는 것 (v1)

- 임의 쉘 명령 실행, 임의 키 입력 시뮬레이션(SendKeys 전체)
- 파일/데이터 삭제
- 결제, 금융 앱 조작
- 다른 사람에게 메시지 전송 (카카오톡 등)

이런 게 필요해지면 "범용 도구로 즉석 처리"가 아니라, 그 하나만을 위한 좁고 명시적인 전용
스킬(3.1 레이어)로 따로 설계/검토 후 추가. DESIGN.md 4.6의 화이트리스트 정신을 "도구
레지스트리 자체를 좁게 유지"로 구현.

## 4. 안전장치 (DESIGN.md 4.6 구체화)

| 장치 | 구현 |
|---|---|
| 킬 스위치 | 트레이 메뉴 "전체 중지" → 실행 중인 루프의 `CancellationToken` 즉시 취소 |
| 감사 로그 | 요청·도구 호출·결과를 로컬 JSONL에 append-only 기록 (`%LocalAppData%\LocalAssistant\audit.log`) |
| 화이트리스트 | 3.3절처럼 "도구 레지스트리에 없음"으로 구조적으로 강제 (LLM 신뢰 안 함) |
| 드라이런 모드 | 트레이 체크박스 ON 시, 각 도구가 실제 실행 대신 "이 도구를 이 입력으로 불렀을 것" 로그만 남기고 가짜 성공 반환 |
| 루프 폭주 방지 | 한 요청당 tool_use 라운드 최대 15회 캡 (01번 문서의 "runaway loop" 위험 대응) |
| 동시 처리 | 대화(Claude API 호출)는 언제든 자유롭게, **도구 실행만** Task Runner 세마포어 1개로 직렬화 — 작업 중에도 다른 질문에 바로 답 가능 (2.2 참고) |

## 5. API 키 보관

최초 1회 설정 창에서 Anthropic API 키 입력 → Windows DPAPI(`ProtectedData.Protect`,
현재 사용자 범위)로 암호화해 로컬 파일에 저장. 평문 저장/로그 출력 금지.

## 6. 컴포넌트별 구현 스케치

- **Hotkey + 채팅 창**: 트레이 앱(WinForms) 안에 `RegisterHotKey` 전역 단축키로 채팅 창을
  보이기/숨기기 토글 (한 번 누르면 뜨고, 다시 누르면 숨음 — 창은 떠 있는 동안 지난 대화가
  그대로 스크롤되는 리스트 + 맨 아래 입력창). Claude.ai 채팅창과 비슷한 느낌.
- **Orchestrator**: `HttpClient`로 Anthropic Messages API 호출, 이번 메시지 + 2.1의 대화
  히스토리를 같이 전달, `tool_use` 블록 파싱 → Tool Registry에서 이름으로 찾아 `Execute` →
  `tool_result`로 돌려보내는 루프. 메시지가 올 때마다 **독립적인 루프를 새로 시작**(동시에
  여러 개 떠 있을 수 있음) — Claude 호출 자체는 안 막힘. 모델: `claude-sonnet-5-5` 기본값
  (계획 정확도 우선, 필요시 추후 비용 최적화).
- **Tool Registry / Task Runner**: `ITool { Name, Description, JsonSchema InputSchema, Execute(JsonElement) }`
  인터페이스. 각 스킬/원시도구가 이걸 구현하며 기존 `LocalAssistant.Engine` 클래스를 그대로
  감쌈 — 엔진 코드 재작성 없음. 실제 `Execute` 호출 전에 `SemaphoreSlim(1,1)`을 먼저 획득 —
  이게 2.2의 "도구 실행만 직렬화"를 구현하는 지점.
- **결과 표시**: 채팅창에 assistant 메시지로 추가 (도구를 여러 번 부르는 동안은 "처리 중..."
  같은 가벼운 표시만 하고, 매 tool_use를 전부 채팅에 노출하진 않음 — 최종 답만 메시지로).

## 7. 토큰/비용 관리

채팅방이 계속 쌓이는 구조(2번)라서, 관리 안 하면 매 요청마다 보내는 대화 기록이 끝없이
커진다 — 이걸 그대로 두면 안 됨. v1에서 실제로 적용하는 것들:

- **대화 기록은 최근 N턴만 API로 전송**: 로컬에는 전체 기록을 다 남기지만(복원/열람용),
  Claude에 보낼 때는 최근 사용자 발화 기준 N턴(기본 20턴)만 잘라서 보냄. 자르는 지점은
  항상 "새 사용자 발화가 시작하는 자리"로 골라서, `tool_use`/`tool_result` 쌍이 중간에
  끊기지 않게 함(끊기면 API가 에러를 냄). 오래된 부분을 요약해서 압축하는 건 당장 안 함 —
  일단 자르는 것부터 시작하고 필요해지면 추가 (단순함 우선)
- **이미지보다 텍스트를 우선**: 스크린샷(이미지)은 텍스트보다 토큰을 훨씬 많이 먹는다.
  크롬 관련 작업은 가능하면 [06번 문서](./06-chrome-extension.md)의 확장 프로그램으로 텍스트를
  직접 읽는 쪽을 우선하고, 스크린샷+Vision은 그게 불가능할 때의 fallback으로 남김
- **캐시로 재조회 자체를 줄임**: 05문서의 Firestore 캐시처럼, 최근에 이미 확인한 정보면
  다시 Claude를 부르지 않고 캐시를 그대로 씀
- **사용량 로그**: 매 API 응답의 `usage.input_tokens`/`output_tokens`를 감사 로그에 같이
  기록. 비용 대시보드 같은 건 아직 안 만듦(과한 범위) — 일단 추적 가능하게만 해둠
- **Prompt Caching 명시적 적용**: Anthropic API는 캐싱이 자동이 아니라 블록에 `cache_control`을
  직접 달아야 적용된다. 시스템 프롬프트(+ 8번의 상시 규칙 파일)와 도구 목록은 매 호출 거의
  고정이므로 여기에 캐시 브레이크포인트를 걸면 캐시 적중 시 입력 토큰 비용이 90% 절감된다.
  주의: 프리픽스의 어떤 부분이든 바뀌면 그 뒤 전부 캐시가 깨짐 — 그래서 날짜처럼 매번 바뀌는
  값은 시스템 프롬프트에 넣지 않고 사용자 메시지 쪽에 둔다
- **모델 티어링: 나중 레버 → 지금 적용**: TimeTree 자동조회([05번 문서](./05-timetree-schedule-skill.md))처럼
  "사람이 직접 묻지 않고 반복 실행되는 단순 작업"은 처음부터 `claude-haiku-5-5`로 고정한다.
  채팅창에서 사용자가 직접 묻는 대화는 계속 `claude-sonnet-5-5` 기본값 유지 — 판단 정확도가
  필요한 경로와 반복적인 저위험 경로를 나누는 것이라, "그냥 한 줄 질문도 분류해서 모델을
  바꾸는" 복잡도는 여전히 안 만듦

## 8. 상시 규칙/기억 파일 (대화 트림에도 안 사라지는 것)

문제: 7번의 대화 트림으로 오래된 턴이 통째로 사라지면, 그 안에 있던 "항상 이렇게 해줘" 같은
사용자 지시나 중요한 결정 근거도 같이 사라진다. 이런 것들은 트림과 무관한 별도의 작은 파일로
빼서 매 요청마다 시스템 프롬프트 뒤에 그대로 붙인다.

- **파일**: `%LocalAppData%\LocalAssistant\memory.md` — 평문 마크다운, 사용자가 직접 열어서
  봐도 됨
- **쓰는 방법**: Claude가 호출하는 작은 전용 도구 `update_memory_note(text)` 하나만 추가 —
  사용자가 "이거 기억해놔" / "앞으로 이렇게 해줘"처럼 말하면 Claude가 판단해서 이 도구로 한
  줄 append (파일을 통째로 재작성하지 않음 — 실수로 기존 규칙을 지우는 사고 방지)
- **읽는 방법**: Orchestrator가 매 요청마다 이 파일을 읽어서 시스템 프롬프트 뒤에 그대로
  붙임 (파일이 없으면 빈 상태로 시작)
- **영구 기록 기준**: 사용자가 명시적으로 "기억해둬"라고 하면 그 자리에서 바로 기록. 그 외
  반복되는 지시는 같은 요청이 3번째 나왔을 때 Claude가 "이거 규칙으로 저장해둘까요?"처럼
  먼저 확인하고 기록 — 한 번 말한 걸로 즉시 영구 규칙화하지 않음
- **캐싱과의 관계**: 이 파일이 시스템 프롬프트의 일부가 되므로, 자주 바뀌면 7번의 캐시
  적중률이 떨어진다. 자주 바뀌지 않는다는 전제로 괜찮음 — 하루에도 여러 번 바뀌는 용도로
  쓰이게 되면 그때 가서 별도 캐시 구간으로 분리

## 9. 단계별 빌드 로드맵

1. **Step 1**: 단축키 + 채팅창 + 도구 없이 Claude 호출만 → 검증: 메시지 몇 개 주고받아도
   이전 대화를 기억하는지 (배관 + 대화 기록 확인)
2. **Step 2**: Tool Registry + `convert_chrome_pdf_to_pptx` 하나만 연결 → 검증: "크롬 PDF를
   PPT로 만들어줘"라고 자연어로 말하면 M1 파이프라인이 실제로 끝까지 돈다
3. **Step 3**: 범용 원시 도구 4~5개 추가 → 검증: 전용 스킬이 없는 낯선 작업(예: "메모장
   열고 '테스트'라고 쓰고 저장해줘")을 Claude가 원시 도구 조합만으로 즉석 처리하는지 확인
4. **Step 4**: 안전장치 UI(킬 스위치/감사 로그 뷰어/드라이런 토글) 트레이에 정리
