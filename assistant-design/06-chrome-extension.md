# 크롬 확장 프로그램 — 텍스트 기반 Chrome 읽기 — 설계도 (v0.1)

> 전제: 03/05문서의 "크롬 화면을 스크린샷 찍어서 Claude Vision으로 읽기" 접근을, 가능한
> 곳에서는 **DOM 텍스트를 직접 읽는 크롬 확장**으로 대체/보완하는 문서. 토큰 비용과
> 안정성 둘 다를 위한 변경. **아직 코드 없음 — 설계만.**

---

## 1. 왜 필요한가

- **토큰 비용**: 스크린샷(이미지)은 텍스트보다 훨씬 많은 토큰을 먹는다. TimeTree 일정처럼
  자주 조회하는 작업(부팅마다, 질문마다)일수록 이 차이가 누적됨 (03문서 7번 참고)
- **안정성**: UIA 트리 읽기는 Chrome이 Electron/Chromium 기반이라 트리가 부실할 수 있다는
  한계가 DESIGN.md 7번에 이미 적혀있었음. 확장 프로그램은 페이지의 실제 DOM에 직접
  접근하므로 이 문제가 없음
- **색깔 같은 스타일 정보까지 정확히**: 05문서의 "초록 바탕+흰 글씨=내 일정" 분류는 사실
  스타일(색상) 정보라서, 스크린샷+Vision으로는 Claude가 "눈으로 보고 추측"해야 했음. 확장은
  `getComputedStyle()`로 각 일정 요소의 실제 배경색 값을 코드로 직접 읽을 수 있어서 훨씬
  정확하고 빨라짐 (Claude 호출조차 필요 없어짐 — JS에서 바로 분류 가능)

## 2. 적용 범위 — 어디에 쓰고 어디에 안 쓰는지

| 작업 | 이 방식 적용? |
|---|---|
| TimeTree 일정 읽기 (05문서) | **적용** — 05문서 2.2의 스크린샷+Vision을 이 방식으로 대체 (DOM 쿼리 + 색상 분류를 확장이 직접 해서 `{me, partner}` 구조화 데이터를 바로 돌려줌) |
| 03문서 3.2의 범용 "웹페이지 읽기" | **적용** — 대상이 크롬 창이면 `dump_window`/`screenshot_window` 대신 이 경로를 우선 시도 |
| M1의 PDF→PPTX 변환 | **적용 안 함** — 이건 "텍스트를 뽑아내기"가 아니라 "페이지를 시각적으로 그대로 복제하기"가 목적이라, 텍스트 추출이 오히려 무의미함. 지금 방식(캡쳐→붙여넣기) 그대로 유지 |

## 3. 구조 — Native Messaging

```
[크롬 확장 (content script + background)]  ◀──Native Messaging──▶  [PC 상주 앱]
     page.querySelectorAll(...) 로 DOM 읽기                      Orchestrator가 "이 탭에서
     getComputedStyle()로 배경색 읽기                              이 정보 읽어줘" 요청
     결과를 구조화 JSON으로 정리
```

- Chrome의 **Native Messaging**(공식 기능)으로 확장과 로컬 PC 앱이 통신 — 네트워크 왕복
  없이 로컬에서 바로 주고받음. 확장은 매니페스트에 등록된 네이티브 호스트와만 통신 가능해서
  보안 모델도 깔끔함
- PC 상주 앱이 Native Messaging Host 역할 (stdin/stdout으로 메시지 주고받는 작은 프로세스
  — .NET 콘솔 실행 파일로 구현 가능)
- 확장은 특정 탭(또는 URL 패턴)에 대해서만 동작하도록 제한 (`matches` — timetreeapp.com 등)
  — 아무 사이트나 다 읽지 않음, 03문서 3.3의 "좁은 화이트리스트" 원칙을 여기에도 적용

## 4. "휴대폰에서도 크롬을 쓸 수 있다"는 것의 의미 — 오해 방지

확장 프로그램 자체는 **PC의 크롬에만** 설치된다. 폰이 이 확장과 직접 통신하는 구조는 아님
— 그렇게 만들면 불필요하게 복잡해짐(인증·연결 관리를 또 만들어야 함). 대신:

- 폰이 "오늘 일정 뭐있어?" 물어보면, 그 요청은 여전히 04문서의 흐름(Firestore → PC
  Orchestrator)대로 PC로 전달됨
- PC가 이 확장을 통해 크롬을 읽고 답을 만들어서 돌려줌
- 즉 "폰에서 PC의 크롬을 쓴다"는 건 **PC가 대신 읽어주는 것**이지, 폰이 그 확장을 직접
  조작하는 게 아님. 이미 PC가 중계하는 구조(04문서)라서 이렇게 해도 기능상 차이는 없음

## 5. TimeTree 스킬에 적용했을 때 구체적으로 바뀌는 것 (05문서 대비)

- 05문서 2.2(스크린샷+Vision) → 확장이 캘린더 DOM에서 각 일정 요소의 텍스트 + 배경색을
  읽어서 색상 기준으로 `{me, partner}`를 **JS에서 직접 분류** → 이미 구조화된 JSON을
  PC 앱에 돌려줌
- 이러면 05문서 2.3("Claude에게 분류를 맡긴다")이 사실 필요 없어짐 — 분류는 확장이 끝냄.
  Claude는 그 구조화 데이터를 받아서 자연어로 답을 다듬는 역할만 하면 됨 (또는 그것도 생략
  하고 그냥 템플릿으로 포맷 가능 — 05문서 4.2의 "폰은 씬 클라이언트" 오프라인 답변 방식과
  동일한 수준으로 단순해짐)
- **트레이드오프**: TimeTree가 웹 UI 구조(클래스명 등)를 바꾸면 DOM 선택자가 깨질 수 있음 —
  스크린샷+Vision은 이 위험이 없었음(Claude가 "보고" 이해하니까). 그래서 **완전 대체가
  아니라 우선 경로로** 두고, DOM 선택자를 못 찾으면 스크린샷+Vision으로 자동 fallback하는
  구조를 권장

## 6. 미결정 사항

- [ ] Native Messaging Host를 PC 상주 앱 자체 프로세스로 할지, 별도 작은 프로세스로
      분리할지
- [ ] DOM 선택자가 깨졌을 때(요소를 못 찾음) → 스크린샷+Vision fallback으로 자동 전환할지,
      그냥 실패로 보고할지
- [ ] 확장이 접근 가능한 사이트 화이트리스트 초안 (최소: timetreeapp.com)

## 7. 로드맵

1. **Step 1**: 최소 확장(매니페스트 + Native Messaging 등록) 만들어서 PC 앱과 "hello"

3. **Step 3**: 05문서의 `check_timetree_schedule` 스킬을 이 경로로 교체, 스크린샷+Vision은
